# ScoreKit: общая инструкция

ScoreKit — переиспользуемый инструмент LilyPond для сборки, проверки, экспорта и публикации партитур. Родительский репозиторий хранит музыкальное произведение и свою редакционную историю; ScoreKit не должен содержать ноты, названия произведений, состав оркестра и музыкальные исключения.

## Структура проекта

`score.ly`, `concert-score.ly`, `orchestra.ily` и `metadata.ily` принадлежат произведению. Исполнители хранятся отдельно в `music/*.ily`, а печатные обёртки — в `parts/*.ly` и при необходимости `parts/combined/*.ly`. Печатные варианты оформляются через `scorekit/lilypond/layout/*.ily`, а колонтитул Git определяется `scorekit/lilypond/version.ily`. Данные о повторах и проверках можно задать в `music/playback-map.json`.

## Сборка

Из корня проекта:

```bash
python3 scorekit/scripts/check_music_structure.py
python3 scorekit/scripts/build.py build
python3 scorekit/scripts/build.py package
```

Для внутреннего MIDI, MP3 и SVG/JSON-просмотрщика (нужны SoundFont, FluidSynth и FFmpeg):

```bash
python3 scorekit/scripts/build.py build --audio --soundfont /path/to/MS_Basic.sf3
python3 scorekit/scripts/build.py package --full
```

Результаты хранятся в `dist/`. Каждый PDF A4 включает Git-версию на каждой странице. `music_hash` отслеживает музыкальные события, `print_hash` — печатное представление; точные байты файла — `pdf_sha256`. Эти хеши не должны зависеть от Git-версии.

## GitHub Actions

В корне проекта остаётся только `.github/workflows/build.yml`: события `push`, `pull_request`, ручной запуск и теги определяются там, так как GitHub не ищет workflow в подмодуле. Сами шаги сборки и релиза расположены в `scorekit/actions/build/action.yml` и `scorekit/actions/release/action.yml`.

При каждом push/PR, ручном запуске или публикации релиза `v*` последовательно выполняются **ровно две задачи**:
1. `PDF score and parts` — печатает партитуры и партии A4, делает PDF-архив и `print-manifest.json`, сразу публикует Actions artifact `score-pdf-<SHA>`.
2. `MIDI, audio, viewer and packages` — скачивает готовые PDF, заново **не печатает** их, генерирует MIDI без PDF, рендерит MP3, SVG/JSON-просмотрщик и дополнительные пакеты; отдельный artifact `score-media-<SHA>`.

После ручной публикации GitHub Release с тегом `v*` ко второму заданию прикрепляются материалы релиза: индивидуальные PDF партий/партитур, один общий PDF-архив, один аудиоархив (только MP3 общего микса и отдельных инструментов), отдельный MP3 общего микса и один архив просмотрщика (SVG, манифест и таймлайн, без дублирования аудиодорожек). Промежуточные файлы не публикуются. Никаких отдельных однофайловых GitHub Actions artifacts нет: Actions в любом случае скачивает их ZIP-архивом.

Для локальной сборки полностью по-прежнему работают `python3 scorekit/scripts/build.py build --audio` и `package --full`. Разделённый режим CI: `build` + `package` для PDF, затем `build --audio --reuse-pdf` + `package --full`; второй режим требует готовых PDF первой стадии.

## Редактирование и повторное использование

В `parts/*.ly` можно указать `#(define partStaffSize 22)` и `#(define partTargetPages 2)`: сборщик подбирает максимально крупный стан, умещающийся на целевое число страниц. Печатные `R2.*N` с `\compressEmptyMeasures` образуют многотактовые паузы; метки репетиций разделяют их только в нужных местах.

Конкретный маршрут исполнения задаётся проектом через `music/playback-map.json`. ScoreKit проверяет соответствие данных `playback_sections` и `navigation`, не пытаясь переписывать партитуру, `metadata.ily` или `global.ily`. Объединённую печатную партию ударных проект поддерживает как обычный нотный исходник; одноразовый генератор удалён.

## Смычковые инструменты и динамика MIDI

Если в музыке изменяется MIDI-инструмент через `\\set Staff.midiInstrument`,
его состояние сохраняется до следующего явного изменения. При репризе
проект должен снова задавать требуемый тембр в начале повторяемого раздела.
ScoreKit проверяет фактические программы MIDI на звучащих нотах во всех
повторных появлениях печатных тактов, независимо от инструмента и типа
репризы. Проверка не требует обязательной смены arco → pizzicato → arco.

LilyPond преобразует `\\p`, `\\mf`, `\\f`, crescendo и diminuendo в
MIDI, а `articulate.ly` учитывает часть штрихов через длительность нот.
FluidSynth озвучивает события через SF3/SF2 SoundFont; в CI используется
MuseScore MS Basic.sf3. MIDI нужен только как промежуточный формат сборки:
не публикуется ни в GitHub Releases, ни в Actions artifacts.

После микширования несжатых WAV проверяется интегральная громкость и истинный
пик. Затем применяется только постоянный уровень усиления, чтобы
автоматическая адаптивная нормализация не сглаживала музыкальную динамику.
MP3 отдельных дорожек и общего микса кодируются через libmp3lame с постоянным битрейтом 192 кбит/с.

## Упорядочивание материалов релиза

Имена сформированных файлов имеют стабильные префиксы для лексикографической
сортировки: `00-` — обычная дирижёрская партитура, `01-` — партитура
в концертном строе, `10-` — индивидуальные и объединённые партии,
`89-` — отдельный MP3 всего оркестра, `90-` — архив PDF,
`91-` — архив MP3, `92-` — архив SVG/JSON.
После префикса сохраняются slug произведения и Git-версия. Графический
интерфейс GitHub может использовать собственный порядок отображения assets;
префиксы обеспечивают ожидаемый порядок при сортировке по имени.



## Актуальная схема сайта партитуры

**Один проект — один сайт — один последний релиз на Pages.**
Внешний каталог, если понадобится, содержит только ссылки на сайты
партитур. В просмотрщике больше нет выбора произвольного репозитория
или исторической версии: актуальный тег и метаданные автоматически
поступают из `viewer/latest.json`.

Только после успешного прикрепления материалов к опубликованному GitHub Release запускается Pages workflow. Обычные push в main и сборки веток сайт не обновляют.
Он получает архив `*-viewer-*.zip` и `*-audio-*.zip` только
последнего релиза, распаковывает SVG, JSON и MP3 в статические файлы
на том же домене Pages и проверяет полноту ресурсов. Старые релизы
остаются в GitHub Releases, но не занимают место на Pages.
Изображения и звуковые дорожки загружаются по мере необходимости:
не нужен CORS с GitHub Release downloads.

Подробная [инструкция просмотрщика](../viewer/README.md).


## Геометрия SVG и независимость хешей

SVG после генерации очищаются от печатных титулов, колонтитулов и
Git-версии; заголовок выводится по центру веб-страницы. Для нот
в `viewer/manifest.json` хранятся реальные границы тактов из
SVG-линеек/тактовых черт (`measure_areas`, `page_viewboxes`),
чтобы текущий такт подсвечивался и можно было нажать на него.
При повторении музыкального фрагмента нажатие выбирает первое
воспроизведение печатного такта.

`music_hash` и `print_hash` рассчитываются по исходникам, не по
SVG или PDF. Они не зависят от значения Git-версии в колонтитулах;
байтовый `pdf_sha256` зависит. В CI это проверяется отдельно.


## Зафиксированная версия LilyPond

Все этапы CI (PDF, MIDI, MP3 и SVG) устанавливают **строго одну версию**
LilyPond из [`scorekit/config/lilypond-version.txt`](../config/lilypond-version.txt).
Сейчас это **2.26.0**. Чтобы обновить LilyPond во всех задачах,
достаточно изменить **одну строку** в этом конфиге. Установка выполняется
универсальным composite action `scorekit/actions/install-lilypond`, который
проверяет, что установленная программа соответствует конфигу. Релиз
`latest` в GitHub API не запрашивается.
